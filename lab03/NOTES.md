Команда git restore появилась в Git 2.23 как более явный инструмент для работы с отдельными файлами. Она копирует чистую версию файла в рабочее дерево, область индексирования (индекс) или в оба места сразу. Ключевое отличие между простым git restore и версией с опцией --source заключается в том, откуда берётся исходная версия файла и куда она помещается
git restore <файл>	Отменяет локальные изменения в рабочем дереве. Если файл был в индексе — перезаписывает его из индекса. Если не был — из HEAD. Неиндексированные изменения теряются безвозвратно.
git restore --source=<коммит> <файл>	Заменяет содержимое и в рабочем дереве, и в индексе на версию из указанного коммита. Ваши правки в обоих местах заменяются на старую версию файла из истории.
git restore --staged <файл>	Убирает файл только из индекса, но оставляет его изменённым в рабочем дереве. Это современная замена команды git reset HEAD 
# Разница между git revert и git reset --hard

## Как это работает

**`git revert`** выполняет три шага:
1.  Берёт отличия, которые внёс целевой коммит.
2.  Строит «обратные» изменения (инверсный diff).
3.  Создаёт **новый коммит**, который применяет эту «обратную разницу» к текущему состоянию ветки.


В результате исходный коммит **остаётся в истории**, но его влияние на код отменяется последующим коммитом. История остаётся линейной и полной
**`git reset --hard`** работает иначе:
*   Перемещает указатель `HEAD` на указанный коммит. 
*   В зависимости от режима (`--soft`, `--mixed`, `--hard`) дополнительно обновляет индекс и/или рабочую директорию.what-does-the-git-reset-command-do/)
*   В режиме `--hard` коммит **исчезает из истории ветки**, а все изменения после него (в индексе и рабочей директории) безвозвратно теряются. 
## В чём ключевое отличие

| Критерий | `git revert` | `git reset --hard` |
|---|---|---|
| **Влияние на историю** | **Добавляет новый коммит**, не переписывая старые. | **Переписывает историю**, удаляя коммиты и их изменения. |
| **Безопасность в команде** | Безопасна для **опубликованных веток**. Другие разработчики, уже получившие коммит, не столкнутся с конфликтами. | **Опасна для опубликованной истории**. Если коммит был пушен другим разработчикам, перезапись истории вызовет расхождения и ошибки у коллег. |
| **Риск потери данных** | Не приводит к потере данных — изменения сохраняются в новом коммите-откате. | **Критический риск**: при неосторожном использовании (например, `git reset --hard` без `git reflog`) можно безвозвратно потерять изменения из рабочей директории и индекса. 

## Почему `revert` безопаснее для опубликованной истории

Представьте, что вы отправили коммит коллеге, он его уже использовал, а потом вы решили переписать историю через `git reset --hard`. У коллеги, который только что получил изменения, возникнет конфликт: его локальная история (коммит уже был) не совпадёт с той, что пришла от вас. Чтобы всё собрать воедино, ему придётся разрешать эти конфликты вручную. 

`git revert` решает эту проблему изящно: вы просто добавляете в историю коммит-откат. Все участники видят чёткую картину: что именно произошло, и могут легко синхронизироваться через обычный `git pull` без риска конфликтов. 

## Когда что использовать

*   **`git revert`** — используйте, когда коммит уже опубликован в удалённом репозитории или когда вы работаете в команде. 
*   **`git reset --hard`** — подходит для локальной отмены коммита, который ещё не был пушен. 

## Важные нюансы

*   Для `git revert` рабочая директория должна быть чистой (без незакоммиченных изменений). 
*   При отмене могут возникнуть конфликты слияния, если после нужного коммита файл менялся ещё раз. Их придётся разрешить вручную. 
*   Если нужно отменить несколько коммитов одним коммитом, можно использовать `git revert --no-commit` (или `-n`). Это применит все отмены к индексу и рабочей директории, но сам коммит автоматически не создаст — вам останется только выполнить `git commit`.
